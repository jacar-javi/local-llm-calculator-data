## 2. Weight bits-per-weight derivations

### 2.1 GGUF (llama.cpp v0.4.1; also used by Ollama and LM Studio's llama.cpp engine)

These are effective file bpw for a full model, taken from `tools/quantize/README.md`. The table was
measured on **meta-llama/Llama-3.1-8B**.

| Type | bpw (measured, Llama-3.1-8B) | size GiB | nominal block bpw (`GGML_QUANT_SIZES`) |
|---|---|---|---|
| F16 | 16.0005 | 14.96 | 16 |
| Q8_0 | 8.5008 | 7.95 | (32 w, 34 B) = 8.5 |
| Q6_K | 6.5633 | 6.14 | (256, 210 B) = 6.5625 |
| Q5_K_M | 5.7036 | 5.33 | Q5_K (256, 176 B) = 5.5 |
| Q4_K_M | 4.8944 | 4.58 | Q4_K (256, 144 B) = 4.5 |
| IQ4_XS | 4.4597 | 4.17 | (256, 136 B) = 4.25 |
| Q3_K_M | 3.9960 | 3.74 | Q3_K (256, 110 B) = 3.4375 |
| IQ3_XXS | 3.2548 | 3.04 | (256, 98 B) = 3.0625 |
| Q2_K | 3.1593 | 2.95 | (256, 84 B) = 2.625 |

These are not in the README table:

- **Q4_0**: the value is derived. `quantize.cpp` gives `" 4.34G, +0.4685 ppl @ Llama-3-8B"`. Parameters
  come from the README F16 row: 14.96 GiB x 2^30 x 8 / 16.0005 = 8.0313e9. Then 4.34 x 2^30 x 8 / 8.0313e9 =
  **4.642 bpw**. As a check, the same method applied to quantize.cpp's other strings gives Q8_0 8.514 (table
  8.5008), Q4_K_M 4.899 (table 4.8944) and Q2_K 3.166 (table 3.1593). The error is under 0.2%, and "G"
  means GiB. Caveat: the strings say Llama-3-8B, while the table uses Llama-3.1-8B, which has the same
  architecture and vocabulary.
- **TQ2_0 / TQ1_0**: only nominal values exist. quantize.cpp says "2.06 bpw ternarization" and "1.69 bpw
  ternarization". Blocks are (256, 66 B) = 2.0625 and (256, 54 B) = 1.6875. No whole-model measurement
  is published, and both types only make sense on ternary-trained models.
- **BF16**: nominal 16. quantize.cpp: `"14.00G, -0.0050 ppl @ Mistral-7B"`.
- **MXFP4_MOE**: 3D expert tensors are MXFP4 (32, 17 B) = 4.25 and every other tensor is Q8_0
  (`src/llama-quant.cpp`).

**What stays unquantized** (`src/llama-quant.cpp`): only 2D/3D tensors whose names end in `weight` are
quantized, so norms stay unquantized. `output.weight`, and `token_embd` when it is tied, become Q6_K for
most k-quant mixes. They become Q5_K for IQ2/IQ3_XXS/IQ1 mixes and Q8_0 when the width is not divisible
by the block. The README documents `--leave-output-tensor`, `--output-tensor-type` and
`--token-embedding-type`.

### 2.2 MLX (mlx v0.32.2 `python/src/ops.cpp` quantize table)

| mode | group sizes (default*) | bits (default*) | scale | bias |
|---|---|---|---|---|
| affine | 32, 64*, 128 | 2, 3, 4*, 5, 6, 8 | same as input dtype | yes |
| mxfp4 | 32* | 4* | e8m0 | no |
| mxfp8 | 32* | 8* | e8m0 | no |
| nvfp4 | 16* | 4* | e4m3 | no |

Formulas, for fp16/bf16 inputs so that scale and bias are 16 bits each:

- affine: `bpw = b + (16 + 16)/g = b + 32/g`
  - g=64: 8-bit **8.5**, 6-bit **6.5**, 5-bit 5.5, 4-bit **4.5**, 3-bit **3.5**, 2-bit 2.5
  - g=32 adds 1.0 bpw and g=128 adds 0.25 bpw
- mxfp4 = 4 + 8/32 = **4.25**; nvfp4 = 4 + 8/16 = **4.5** (plus an optional fp32 global scale per
  tensor); mxfp8 = 8 + 8/32 = **8.25**
- Packing: data goes into uint32 words. Non-power-of-two bit widths are bit-stream packed
  (`pack_and_quantize`), so the only waste is word padding at the end of each row.
- **Embeddings and lm_head are quantized too**: `nn.Embedding` implements `to_quantized`, and
  `mlx_lm.utils.quantize_model` only skips a module when `weight.shape[-1] % group_size != 0` or a
  predicate excludes it.
- mlx-lm convert defaults are `affine (64, 4)`, `mxfp4 (32, 4)`, `nvfp4 (16, 4)` and `mxfp8 (32, 8)`.
  Mixed recipes `mixed_2_6`, `mixed_3_4`, `mixed_3_6` and `mixed_4_6` raise the first 1/8, the last 1/8
  and every third layer. The resulting bpw is printed by `compute_bits_per_weight` (bytes x 8 / params).
- Ollama's MLX engine (`x/quant/quant.go`) maps int4 to affine g64 (4.5) and int8 to affine g64 (8.5), plus
  nvfp4/16, mxfp4/32 and mxfp8/32. **Ollama aliases "FP8" and "Q8" to int8 affine**, which is not float8.
- oMLX oQ levels are documented targets: oQ2 ~2.9, oQ2.5 ~3.2, oQ2.7 ~3.3, oQ3 ~3.5, oQ3.5 ~3.8, oQ4 ~4.6,
  oQ5 ~5.5, oQ6 ~6.5, oQ8 ~8.6. The base is affine g64, or mxfp8 g32 for oQ8.

### 2.3 vLLM v0.29.0 / SGLang v0.5.19 (HF safetensors checkpoints)

| Format | Group | Layout (code) | bpw formula | bpw |
|---|---|---|---|---|
| FP16/BF16 | n/a | n/a | 16 | 16 |
| FP8 W8A8 | per-channel (FP8_DYNAMIC) or per-tensor (ModelOpt FP8) | fp8 + scale per channel/tensor | 8 + ~0 | ~8.0 |
| AWQ 4-bit | 128 (auto_awq.md `q_group_size: 128`, `zero_point: True`) | qweight int32-packed, qzeros 4-bit packed per group, scales `params_dtype` | 4 + (16+4)/128 | **4.156** |
| GPTQ 4-bit | 128 (gptqmodel.md `group_size=128`) | as AWQ + `g_idx` int32 per input column | 4 + 20/128 + 32/out_features | **~4.16** |
| compressed-tensors W4A16 | 128, `symmetric=True` (llm_compressor/int4.md) | int4 + bf16 scale | 4 + 16/128 | **4.125** |
| NVFP4 (ModelOpt) | 16 (`modelopt.py group_size=16`) | uint8-packed fp4 + `float8_e4m3fn` scale + fp32 `weight_scale_2` | 4 + 8/16 | **4.5** |
| MXFP4 | 32 (`OCP_MX_BLOCK_SIZE`) | uint8 + e8m0 uint8 scale | 4 + 8/32 | **4.25**, experts only |

- **Unquantized layers in the docs**: llm-compressor recipes use `ignore=["lm_head"]` for W4A16 and
  FP8_DYNAMIC. The FP8 doc says "all Linear modules (except for the final `lm_head`)". vLLM's MXFP4 only
  quantizes routed experts: "MXFP4 linear layer is not implemented - falling back to
  UnquantizedLinearMethod", and attention is skipped as well. SGLang marks `mxfp4` as "MOE-only".
- vLLM hardware table: AWQ and GPTQ are unsupported on AMD GPU and Arm CPU. llm-compressor FP8 W8A8
  runs on Ada, Hopper and AMD GPU. SGLang picks Marlin (W4A16) for NVFP4 on SM80-SM90.
- SGLang on Apple uses MLX: `--quantization mlx_q4` / `mlx_q8` means group 64, giving 4.5 and 8.5 bpw.

**Flash attention requirements**

- llama.cpp v0.4.1 (`src/llama-context.cpp`): a quantized V cache with `-fa auto` (the default) turns FA on
  ("enabling flash_attn since it is required for quantized V cache"). With `-fa off` it fails. When FA is
  on, every quantized K or V needs head_dim divisible by the block size. MLA models (and DeepSeek4) reject
  different K and V types.
- Ollama v0.34.0: `OLLAMA_FLASH_ATTENTION` unset means `--flash-attn auto` if every device supports FA
  (CPU, Metal, ROCm and Vulkan always count as supported; CUDA needs compute >= 6, not 7.2, and driver
  major >= 7), otherwise `off`. Setting it to 0 forces `off`, which then breaks a quantized V cache.
- LM Studio: the V cache "requires Flash Attention to be enabled". FA is on by default for CUDA (0.3.31)
  and for Vulkan and Metal (0.3.32).

**MLA cache sizes**

- llama.cpp: K only, `n_embd_k_gqa = (kv_lora_rank + qk_rope_head_dim) x 1 head` (`has_v = !is_mla`).
- vLLM: `MLAAttentionSpec` with `num_kv_heads=1` and `head_size_v = 0`.
- SGLang: `kv_cache_dim = kv_lora_rank + qk_rope_head_dim`.
- mlx-lm DeepSeek V3: caches `kv_latent` and `k_pe`.
- ExLlamaV3: `ckv (kv_lora_rank)` + `kpe (rope)`.

## 4. Memory policies

### llama.cpp v0.4.1 (`ctx-prealloc`)

- `-c` defaults to 0, which means `n_ctx_train`. The server README says "0 = loaded from model".
- `--fit` defaults to on (`common.h fit_params = true`). If projected use exceeds free memory minus
  `--fit-target` (1024 MiB per device), an unset context is lowered linearly toward `--fit-ctx` 4096, and
  then layers or experts move to CPU. `common/fit.cpp` logs "context size set by user ... -> no change"
  when `-c` was given. `-c 0` given explicitly disables the reduction (`fit_params_min_ctx = UINT32_MAX`).
- Server parallelism: `-np` defaults to -1 (auto). `server.cpp` then sets `n_parallel = 4` and
  `kv_unified = true`.
- `llama-context.cpp`: `n_ctx = GGML_PAD(n_ctx, 256)`. Unified KV gives `n_ctx_seq = n_ctx`; otherwise
  `n_ctx_seq = n_ctx / n_seq_max` across `n_stream = n_seq_max` streams. The KV tensor is
  `[n_embd_k_gqa, kv_size, n_stream]`, so **total cells = n_ctx either way**: parallel does not multiply
  the KV cache.
- What does multiply with the slot count: the recurrent state (`recurrent_rs_size = max(1, n_seq_max)`,
  F32) and the SWA window when unified (`n_swa * n_seq_max + n_ubatch`).
- `--kv-unified-per-slot N` sizes the pool as `n_parallel * N` when `-c` is unset.

### Ollama v0.34.0 (`ctx-prealloc`)

- Default `num_ctx` (`server/routes.go`): total VRAM is the sum of `gpu.TotalMemory - OLLAMA_GPU_OVERHEAD`.
  At >= 47 GiB it is 262144, at >= 23 GiB 32768, otherwise 4096. Code comment: "Use slightly lower
  thresholds (47/23 GiB vs. 48/24 GiB)". Docs say <24 GiB 4k, 24-48 GiB 32k, >=48 GiB 256k.
- Precedence: request `num_ctx`, then Modelfile, then `OLLAMA_CONTEXT_LENGTH`, then the VRAM tier. The
  value is capped at the training context (`llm/server.go`).
- On Apple Silicon, ggml's Metal device reports `recommendedMaxWorkingSetSize` as total memory (read in
  llama.cpp v0.4.1 `ggml-metal-device.m`). Ollama's pinned b10760 was not re-read.
- `OLLAMA_NUM_PARALLEL` defaults to 1. llama-server is launched with `-c NumCtx*numParallel -np numParallel`
  and no `-kvu`, so **KV multiplies with parallel**.
- `num_parallel` is forced to 1 for embeddings and for mllama, qwen3vl, qwen3vlmoe, qwen35, qwen35moe,
  qwen3next, lfm2, lfm2moe, nemotron_h, nemotron_h_moe and nemotron_h_omni.
- Automatic num_batch (also passed as `-ub`): >32768 gives 2048, >4096 gives 1024, otherwise 512. It
  steps down when predicted VRAM exceeds 60% (2048) or 75% (1024) of available memory, or when the
  surcharge would cross 80%.
- On a load OOM, an automatic context is retried once at 32768 or 4096.

### LM Studio 0.4.24

- Max Concurrent Predictions defaults to 4 with Unified KV Cache on. The 0.4.0 notes say this "should
  result in no additional memory overhead", and the SDK says disabling it "ensures each prediction can
  utilize the full context length, at the cost of using more memory".
- Guardrails: estimates cover context length, GPU offload, FA and vision (0.3.27). `lms load --estimate-only`
  reports `passesGuardrails` (`EstimatedResourcesUsage.ts`). Users can override. The tier names and
  thresholds are **not in any fetched doc**, so they are `null`.
- `gpuStrictVramCap` caps offload to detected VRAM.
- Default context is `null`. 0.3.2 cut it from 8K to 4K, and 0.3.24 added an app-wide "default context
  length" setting whose current default is undocumented.

### vLLM v0.29.0 (`fraction-prealloc`)

- `gpu_memory_utilization` defaults to **0.92** (`vllm/config/cache.py`), "per-instance limit".
- `requested = ceil(total x util)`. Startup fails if free memory is below requested.
- `available_kv = requested - non_kv_cache_memory (weights + peak activation + non-torch) - cudagraph_estimate`
  (`gpu_worker.py`). The CUDA-graph estimate is on by default via `VLLM_MEMORY_PROFILER_ESTIMATE_CUDAGRAPHS=1`.
- `kv_cache_memory_bytes` bypasses the fraction.
- `max_model_len` defaults to the model config value, and `-1`/`auto` picks the largest that fits.
  `check_enough_kv_cache_memory` requires the pool to hold one `max_model_len` request.
- The pool is shared paged blocks (block_size 16), so parallel does not multiply the KV cache.

### SGLang v0.5.19 (`fraction-prealloc`)

- `mem_fraction_static` defaults to None. `arg_groups/memory_hook.py` computes
  `(gpu_mem - reserved_mem)/gpu_mem`, where reserved_mem (MB) is
  `512 + 1.5*max(chunked_prefill,2048) + tp*pp/8*1024 + 2*decode_max_bs + 8*len(prefill_graph_bs)`, with MLA
  prefill graphs counted as 1.5 GiB and a floor of 10 GiB when gpu_mem > 60 GiB. It is 0.88 if GPU memory
  is unknown.
- Worked example (derived, not documented) for a 24 GiB GPU: chunked_prefill 2048, decode max_bs 24, and
  42 prefill graph sizes up to 2048. That gives 512 + 3072 + 128 + 48 + 336 = 4096 MB, so the fraction is
  about 0.833 (0.847 without prefill graphs). Whether prefill CUDA graphs are enabled by default was not
  verified.

### mlx-lm v0.31.3 (`on-demand`)

- `KVCache` grows in 256-token steps. `QuantizedKVCache` also steps by 256.
- The wired limit is set to `max_recommended_working_set_size` during generation.
- Server: `--decode-concurrency 32`, `--prompt-concurrency 8`, `--prompt-cache-size 10`.

### oMLX v0.6.4 (`ceiling`)

- `ProcessMemoryEnforcer`: ceiling = min(static, dynamic, metal_cap).
- static = RAM - reserve, where the reserve is safe 8 GiB, **balanced 6 GiB (default)**, aggressive 4 GiB
  or custom 2 GiB. Machines under 24 GiB always reserve 4 GiB.
- dynamic = phys_footprint + free + inactive + active x {0.2, 0.5, 0.8}, or the user-supplied GB for custom.
- metal_cap = `iogpu.wired_limit_mb` if set, otherwise `max_recommended_working_set_size`.
- Soft and hard watermarks: soft is 0.85/0.90/0.925/0.85 by tier, hard is 0.95.
- Context: the native context when discovered, falling back to 32768.
- `max_concurrent_requests` defaults to 8.

### ExLlamaV3 v1.5.0 (`ctx-prealloc`)

- `Cache(model, max_num_tokens)` allocates 256-token pages at load. The pool is shared across jobs
  ("seq_len * batch_size <= max_num_tokens").
- `max_batch_size` 16 sets the number of recurrent slots.

## 5. Contradictions found (docs vs code, or docs vs docs)

1. **Ollama default context.** `docs/faq.mdx` says "By default, Ollama uses a context window size of 4096
   tokens." `docs/context-length.mdx` and `server/routes.go` use VRAM tiers 4k/32k/256k.
2. **Ollama tier boundaries.** The docs say 24/48 GiB; the code uses 23/47 GiB on purpose.
3. **vLLM gpu_memory_utilization.** Code default is 0.92, but docs pages (`design/metrics.md`,
   `usage/usage_stats.md`, benchmark examples) still show 0.9.
4. **vLLM CPU KV space.** `docs/configuration/conserving_memory.md` says `VLLM_CPU_KVCACHE_SPACE` defaults
   to 4 GiB. In `envs.py` it is `None` when unset, and `cpu_worker.py` then auto-sizes the KV cache from
   requested memory minus RSS.
5. **vLLM TurboQuant ratios.** The docstring says `turboquant_k3v4_nc` is "~3.5x", but the packed-size
   formula gives about 4.3x at head_dim 128 (118 B vs 512 B). The other presets match the formula
   (2.6x, 3.8x, 4.9x-5.0x).
6. **oMLX memory limit.** The README says "Total memory limit (default: system RAM - 8GB)". Code at v0.6.4
   defaults to tier `balanced`, which is RAM - 6 GiB. 8 GiB is the `safe` tier.
7. **oMLX soft threshold.** `MemorySettings.soft_threshold` defaults to 0.85, while
   `_SOFT_THRESHOLD_BY_TIER['balanced']` is 0.90. The code treats a saved 0.85 as legacy.
8. **oMLX oQ doc.** "Mandatory Protection (Always Applied): lm_head 8-bit" conflicts with "Minimal
   Protection (oQ8): lm_head: 6-bit".
9. **mlx-lm quantized_kv_start.** The CLI default is 5000 (`DEFAULT_QUANTIZED_KV_START`), but the
   `generate_step` and `speculative_generate_step` Python API defaults are 0.
10. **MLX platforms.** `install.rst` documents CUDA and CPU on Linux only. PyPI mlx 0.32.2 also ships
    `win_amd64` (CUDA 12/13 and CPU) and `win_arm64` (CPU) wheels.
11. **llama.cpp quantize data.** The README table is Llama-3.1-8B, while the option strings in
    `quantize.cpp` cite Llama-3-8B and Mistral-7B.
12. **ExLlamaV3 README** links `doc/exl3.md`, which is missing at v1.5.0.
13. **SGLang Apple Metal.** `hardware-platforms/apple_metal.mdx` exists and is linked from `install.mdx`,
    but it is not listed in `hardware-platforms/overview.mdx`.
14. **mlx-lm pin mismatch.** oMLX pins mlx-lm commit `ab1806e` ("v0.31.3" per its comment), which is not
    the v0.31.3 tag commit `ed1fca4`. It is a later main commit.

## 6. Experimental and partial-support flags

- **llama.cpp**: the OpenVINO backend is "[In Progress]".
- **vLLM**
  - GGUF is "highly experimental and under-optimized" and moved to `vllm-gguf-plugin`.
  - NVFP4 checkpoints log "the format is experimental and could change".
  - The macOS Apple Silicon CPU build is "experimental" and source-only.
  - Apple GPU works only through the community vLLM-Metal plugin (MLX backend).
  - Intel XPU "initially supports basic model inference"; pipeline parallel on XPU is beta.
- **SGLang**
  - FP4 KV cache is "currently experimental".
  - XPU graph and XPU P/D disaggregation are `[Experimental]`.
  - MXFP4 is MoE-only.
- **Ollama**
  - The MLX engine is an optional build; it is on by default on macOS arm64, and MLX CUDA is a separate
    package.
  - Hybrid and VL families are forced to num_parallel=1.
- **oMLX**: multi-Mac distributed inference is "Experimental".
- **ExLlamaV3**
  - CPU MoE offload is "Experimental".
  - ROCm is undocumented; there is only a HIP compile flag in setup.py.
- **LM Studio**: MLX parallel requests are "coming soon" per the docs. `autoFit` is Bionic-only.
